# ADR 0001: Kunci internal memakai BIGINT identity

Status: Diterima, 2026-11-05
Fase siklus hidup: Pengembangan (belum ada data produksi)

## Konteks

Skema awal memakai UUID untuk semua kunci. Sistem ini melayani satu kedai,
dioperasikan dari satu perangkat kasir, dan tim ingin ID yang pendek serta
mudah diperiksa saat debugging.

## Keputusan

- Semua tabel internal memakai `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- `profiles.id` tetap `UUID` karena harus sama dengan `auth.users.id`
  milik Supabase Auth.
- Pengenal yang dibaca manusia dan dicetak di struk adalah `orders.order_no`
  (`TRX-YYYYMMDD-NNNN`), kolom terpisah dari kunci.
- API dan validasi memakai `identifierSchema` (bilangan bulat positif,
  maksimum `Number.MAX_SAFE_INTEGER`).

## Konsekuensi

- ID berurutan dapat ditebak dan menunjukkan perkiraan volume penjualan.
  Setiap endpoint wajib memeriksa kepemilikan toko pada objek yang diakses;
  kerahasiaan ID tidak boleh dianggap sebagai otorisasi.
- Order tidak dapat diberi ID di perangkat sebelum terkirim ke server. Antrean
  offline harus memakai kunci klien terpisah (`Idempotency-Key`) dan menerima
  ID dari server. Bila kelak diperlukan pembuatan order sepenuhnya offline,
  keputusan ini perlu ditinjau ulang.
- Menggabungkan data dari beberapa database akan bentrok. Penambahan cabang
  dimodelkan sebagai baris `stores` dalam satu database, bukan database terpisah.
- Memindahkan ke UUID setelah ada data produksi memerlukan migrasi semua kunci
  asing. Keputusan ini sulit dibatalkan setelah rilis pertama.
- Seed yang memakai ID eksplisit wajib menyelaraskan sequence (`setval`).
